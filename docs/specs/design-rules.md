# デザイン制作のルール

GOOD ORDER / GOOD LOOP の Figma 作業で、AI と天真の間で必ず守るルール。
**このファイルに書かれていることは「お願い」ではなく前提条件。** 破った成果物は納品扱いにしない。

対象ファイル：`UTUTU`（fileKey `KGPuY4YVRQW6BMRrulBaFN`）

---

## 1. 進め方

### 1-1. ピクセルを作る前に、操作の流れを文章で合意する

いきなり Figma を触らない。先に以下を文章で出し、天真の合意を取る。

- 画面遷移（どこから入って、どう戻るか）
- 各画面で人が何をするか
- 状態の一覧（通常／空／0件／エラー／ローディング／確認）

**「作ってから直す」は禁止。** 合意を取らずに作ったものは、作り直しになっても抗議しない。

### 1-2. 案は必ず3つ出す

天真が1案を提示した場合も、**それ以外に2案を足して合計3案**にする。1案だけ出して却下されると、ゼロからやり直しになり時間が倍かかる。

- 3案は**比較できる形**で出す。中身（項目・文言）は揃え、**器だけを変える**
- 各案に「どういう店舗・状況で強いか」を1行添える
- 明らかに劣る当て馬を混ぜない。3案とも本気で作る

### 1-3. 指示されていない次工程に進まない

デザインを頼まれたらデザインまで。**DBスキーマ・実装・マイグレーションには勝手に進まない。**
必要だと思ったら「必要です」と言って止まる。

### 1-4. 判断が要る場面では止まる

仕様に書かれていないことを勝手に決めない。決めた場合は**決めたことを明示**して、いつでも覆せる状態にする。
（例：「項目の入力方式はテキストエリアにしました」→ これは相談すべきだった）

## 2. 作るもの

### 2-1. PC を作るときは必ず SP も対で作る

例外は「**PC版だけ**」と明示して依頼されたときのみ。
GOOD ORDER はモバイルオーダーなので、お客様側は SP が主。

### 2-2. 必須の状態セット

画面を作ったら、以下のうち**その画面に起こりうるものを全部**作る。1枚だけ作って終わりにしない。

| 状態 | いつ必要か |
|---|---|
| 通常 | 常に |
| 空（データが0件） | 一覧・リストがある画面 |
| 絞り込み結果0件 | 検索・絞り込みがある画面 |
| ローディング | 通信を伴う画面 |
| エラー | 通信・保存を伴う画面 |
| 削除確認 | 削除操作がある画面 |

### 2-3. 既存の共通コンポーネントを使う

ボタン・チップ・タブ・フォーム・モーダルなどを**生の Frame で自作しない。**
既存に無い場合は、自作する前に「無いので作ります」と申告する。

## 3. ファイルの構造

```
ページ（MobileOrder など）
└ セクション（機能名 / 日本語名）      ← 最上位。x=0 に揃えて縦積み、間隔100px
   ├ セクション「PC」                  ← 上・左パディング100px
   │  └ フレーム（Template / xxx）     ← 上・左パディング100px、間隔100px
   └ セクション「SP」
      └ フレーム
```

### 3-1. パディングは3箇所すべて100px

- 最上位セクション同士：**100px**
- セクション内の PC / SP セクション：**100px**（上下左右）
- PC / SP 内のフレーム：**100px**（上下左右、フレーム同士の間隔も）

### 3-2. 命名

| 対象 | 形式 | 例 |
|---|---|---|
| 最上位セクション | `英語名 / 日本語名` | `Menu Management / メニュー管理` |
| サブセクション | `PC` / `SP` | — |
| 画面フレーム | `Template / 画面名 幅x高` | `Template / Menu Management 1180x820` |
| モーダル | `Modal / 名前 — PC` | `Modal / ベストセラー設定 — PC` |

### 3-3. セクションにはオートレイアウトが効かない

SP に画面が増えても PC 側は自動でずれない。**放置すると重なる。**
だから 4-1 の整理整頓を毎回やる。

---

## 4. 完了の定義

作業の最後に、以下が全部済んでいて初めて納品。

### 4-1. 整理整頓する

セクション・サブセクション・フレームを、3-1 のパディング基準どおりに並べ直す。
**制作の途中で崩れるのは構わない。終わったときに崩れているのが問題。**

### 4-2. 検品を通す

```
npm run design:figma
```

- **構造・パディング**：0件でなければ納品しない
- **今回増えた違反**：0件でなければ納品しない
- 既存分（ベースライン）は対象外

### 4-3. スクリーンショットを提示する

作った画面を天真に見せる。**「Figma を見てください」で終わらせない。**

## 5. 手戻りが起きたときにやること

同じ指摘を2回受けたら、それは記憶ではなく仕組みの問題。**このファイルかチェックスクリプトに足す。**

| 段 | 置き場所 | 強さ |
|---|---|---|
| 1 | その場の会話 | 1回きり。忘れられる |
| 2 | **このファイル** | 毎回読まれる（＝お願いの最上位） |
| 3 | **`npm run design:figma`** | **破れない（＝制約）** |

判定できるようになったものは、2 から 3 に上げる。

---

## 6. Figma への書き込みについて

- **明示的に依頼されたときだけ書き込む。** 読み取りは自由
- 既存のコンポーネント（`Components` ページ）を変更するときは、**影響範囲を先に伝える**
- 大きく作り替える前に、元のフレームを複製して残す。破壊的変更をいきなりやらない
