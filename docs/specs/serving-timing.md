# 提供タイミングの指定と、伝票の2枚出し

**状態: 仕様案（2026-09-04、天真の確認待ち）。** 決まった項目から「確定」に書き換える。
決まっていない項目は末尾「9. 決めてほしいこと」にまとめてある。

---

## 1. 何を作るか（3機能）

| # | 機能 | 誰のため |
|---|---|---|
| ① | FOOD と DRINK の両方が入った注文は、同じ伝票を**2枚**出す | 厨房とドリンク場に1枚ずつ渡すため |
| ② | パンケーキ・フレンチトーストは、提供を**「でき次第」か「食後」**から選べる。伝票にも印字 | 甘いものを食後に食べたいお客様 |
| ③ | DRINK は、提供を**「先出し」か「食後」**から選べる。伝票にも印字 | 食後のコーヒー等 |

②と③は「提供タイミングをお客様が選ぶ」という同じ仕組みで、文言だけが違う。
以下では②③をまとめて **提供タイミング** と呼ぶ。

---

## 2. 用語と判定

| 用語 | 意味 | どこで決まるか |
|---|---|---|
| FOOD / DRINK | カテゴリーの区分 | `categories.category_type`（管理画面「カテゴリ管理」の「区分」） |
| 対象カテゴリー | 提供タイミングを選べるカテゴリー | `categories.serving_timing_choice`（**新設**。管理画面のトグル） |
| 選択肢 | 区分で決まる。FOOD: でき次第 / 食後、DRINK: 先出し / 食後 | コード側の固定文言 |
| 初期値 | FOOD: でき次第、DRINK: 先出し | コード側 |

- 対象カテゴリーの初期設定: **パンケーキ・フレンチトースト・DRINK区分の全カテゴリーをON**、他はOFF（SQLで投入）。
- 以下は提供タイミングを**選べない**（表示もしない・保存もしない）:
  - テイクアウト注文（`orderType = takeout`）— 持ち帰るので「食後」が成り立たない
  - 店内注文に混ざったテイクアウト商品（`menu_items.is_takeout = true`）— 同上
  - 対象カテゴリーでない商品

## 3. お客様側の操作の流れ

```
一覧（TOP / カテゴリー）
  ├─ 商品を開く → 商品詳細 ─ 提供タイミングを選ぶ ─ カートに入れる ─┐
  └─ カードの「カートに入れる」（詳細を開かない）＝ 初期値で入る ────┤
                                                                      ▼
                                                                    カート ─ 行ごとに提供タイミングを変えられる
                                                                      ▼
                                                                    注文を確定する
                                                                      ▼
                                                                    完了画面（ご注文内容に「食後」を表示）
```

### 3-1. 商品詳細（Product Detail 80:894）

- 対象商品のとき、本文（説明文）の下に「提供タイミング」の選択が出る。初期値が選ばれた状態。
- 選んで「カートに入れる」を押すと、その提供タイミングつきでカートに入る。
- 対象外の商品では今までと何も変わらない。

### 3-2. 一覧からの「カートに入れる」（Menu Card M）

- カードには選択を置かない（カードが縦に伸びてカルーセルが崩れる）。**初期値で入る。**
- 変えたければカートで変える（3-3）。

### 3-3. カート（Cart 364:2216）

- 対象商品の行に、現在の提供タイミングが出ていて、その場で切り替えられる。
- **同じ商品でも提供タイミングが違えば別の行**（例: パンケーキ×1 でき次第、パンケーキ×1 食後）。
  行の同一性は「商品ID ＋ 提供タイミング」で決める。
- 注文を確定すると、行ごとの提供タイミングが明細（`order_items.serving_timing`）に保存される。

### 3-4. 完了画面（Order Confirmed 388:2335）・注文履歴

- 「ご注文内容」の商品名の横に **「食後」だけ**小さく表示する（初期値のときは何も出さない）。
  お客様が確認したいのは「食後にしたことが伝わっているか」であって、初期値の再掲ではないため。
- 履歴からの「同じ内容で注文」は提供タイミングも引き継ぐ。

## 4. 店舗側

### 4-1. 伝票（`lib/receipt.ts`）

- 明細行の品名の下に提供タイミングを印字する。
  - **「食後」は黒帯（白抜き）で強調**。厨房が見落とすと事故になるのはこちら。
  - 「でき次第」「先出し」は通常の文字で印字（案。9-2 参照）。
  - 対象外の商品には何も印字しない。
- **2枚出し**: 注文に FOOD と DRINK の両方が含まれるとき、同じ内容の伝票を続けて2枚印刷する（間でカット）。
  片方だけの注文は今までどおり1枚。
  - 見出し（右上）は 1枚目「厨房伝票」、2枚目「ドリンク伝票」にする案（9-3 参照）。
  - 印刷ジョブは**1注文1ジョブのまま**。1つのジョブの中で伝票を2回組み立てて2回カットする。
    刷り直し（`/admin/print`）も1操作で2枚出る。二重印刷を防ぐ仕組み（`print_jobs.order_id` の UNIQUE）は触らない。

### 4-2. 厨房画面（`/admin/kitchen`、Order Card 222:967）

- 品目行の商品名の横に提供タイミングを出す。「食後」は墨色の小さなチップ、「でき次第」「先出し」は薄い文字。
- 伝票と画面で見えるものを揃える（伝票にあって画面に無い、を作らない）。

### 4-3. 管理画面「カテゴリ管理」

- 編集パネルの「区分」の下に、トグル「提供タイミングをお客様が選べる」を足す。
- 補足文: 「フードは『でき次第 / 食後』、ドリンクは『先出し / 食後』から選べるようになります」。

### 4-4. レジ・受渡画面

- 変更なし（提供タイミングは金額に関係しない）。

## 6. 選択UIの3案（器だけを変える。中身は同じ）

中身（共通）: ラベル「提供タイミング」、選択肢2つ、初期値が選ばれている、タップで切り替え。
既存部品を使う。無いものは「無いので作る」と明記。

| 案 | 器 | 商品詳細 | カート行 | 既存部品 | 強い店舗・状況 |
|---|---|---|---|---|---|
| **A セグメント** | 1つの枠を左右に割った切替 [でき次第｜食後] | 説明文の下に1本 | 価格・数量の下に1本 | **無い → 作る**（管理画面の「表示設定」にある Segment を部品化） | 常連が多く説明が要らない店。注文点数が多くても画面が縦に伸びない |
| **B 説明つきカード** | 縦2枚のカード。各カードに補足1行（「お料理と一緒にお持ちします」「お食事のあとにお持ちします」） | 説明文の下に2枚 | 「食後 ▾」チップ → タップで半モーダル（Call Staff と同じ器）に同じ2枚 | Option Card 180:167 ＋ 半モーダル 184:808 | 初来店が多い店。「先出し」「食後」の意味を伝えたい（リオープン直後の YORKYS 向き） |
| **C チップ** | 丸チップ2つを横並び。選択はアクセント塗り | 説明文の下に横並び | 価格・数量の下に横並び | Filter Chip 46:32（chevron 無しの派生。高さは 44 に上げる） | 将来「食前・食中・食後」のように選択肢が増える可能性がある店。既存の絞り込みUIと同じ見た目 |

AI の推奨: **A**。理由は、カート行にも同じ部品をそのまま置けて画面が最も短く済むこと、
2択が固定なので「増やせる」利点（C）が効かないこと。ただし新規部品を1つ作る。

## 7. データの形（DBスキーマの変更。天真の確認が要る）

新規ファイル `supabase/serving_timing.sql`（既存ファイルは書き換えない）。
**本番の Supabase なので AI は流さない。天真がダッシュボードの SQL Editor で実行する。**

| 変更 | 中身 |
|---|---|
| `categories.serving_timing_choice` | boolean、既定 false。初期投入でパンケーキ・フレンチトースト・DRINK区分を true |
| `order_items.serving_timing` | text、NULL可。CHECK: `'asap'`（でき次第）/ `'first'`（先出し）/ `'after_meal'`（食後）。NULL = 選択対象外 |
| `place_order()` | 明細に `serving_timing` を受け取り、上記3値以外は拒否 |
| `claim_print_job()` | 返す明細に `servingTiming` と `categoryType` を足す（2枚判定と印字に使う） |

- 値を「標準／食後」の2値ではなく3値にするのは、後でカテゴリーの区分を変えても過去の伝票の意味が変わらないようにするため。
- RLS は触らない。anon の権限は増やさない（`place_order` の中で検証する）。
- カートの保存キー `orderly-cart` は変えない。古い保存データに提供タイミングが無い場合は初期値として扱う。

## 9. 決めてほしいこと

番号で答えられるようにしてある。「全部推奨で」でも可。

1. **選択UIの器**: A セグメント（推奨）／ B 説明つきカード／ C チップ
2. **伝票の印字**: (1) 対象商品は全部印字し「食後」だけ黒帯（推奨）／ (2) 「食後」のときだけ印字
   - (1) は厨房が「指定なし＝初期値」と読み替えなくて済む。(2) は紙が短い
3. **2枚目の見出し**: (1) 1枚目「厨房伝票」2枚目「ドリンク伝票」（推奨）／ (2) 両方「厨房伝票」で完全に同一／ (3)「厨房伝票 1/2」「厨房伝票 2/2」
4. **対象の決め方**: (1) カテゴリーごとのトグル（推奨。初期値はパンケーキ・フレンチトースト・DRINK全部ON）／ (2) 商品ごとのトグル
5. **お客様に見える文言**: 「提供タイミング」「でき次第」「食後」「先出し」— このままでよいか
6. **完了画面・履歴**: (1) 「食後」だけ表示（推奨）／ (2) でき次第・先出しも表示
7. **初期値**: FOOD=でき次第、DRINK=先出し でよいか
